# 추천 지역 선정 로직

## 1. 개요

추천 지역 기능은 모임 참가자들의 출발 위치를 기반으로 모두가 이동하기 적절한 지역을 선정하는 기능이다.

단순히 참가자 위치의 중심과 가까운 지역을 선택하는 것이 아니라, 실제 모임 장소로 활용하기 적합한 지역을 후보로 생성한 뒤 참가자별 대중교통 이동시간을 비교하여 최종 추천 지역 TOP3를 선정한다.

전체 흐름은 다음과 같다.

```text
참가자 출발 위치 조회
        ↓
중심 좌표 계산
        ↓
OpenAI 지역 후보 생성
        ↓
Google Places 후보 검증 및 대표 좌표 조회
        ↓
중심 좌표 기준 5km 검증
        ↓
Google Routes Matrix 이동시간 계산
        ↓
평균 / 최대 / 표준편차 계산
        ↓
Min-Max 정규화 및 추천 점수 계산
        ↓
TOP3 선정
        ↓
RecommendationRun / RecommendedArea 저장
```

---

## 2. 중심 좌표 계산

추천 지역 탐색의 기준점을 만들기 위해 참가자들의 출발 위치를 사용한다.

각 참가자의 출발 위도와 경도의 산술 평균을 계산하여 중심 좌표를 구한다.

```text
centerLatitude
= 참가자 출발 위도의 합 / 참가자 수

centerLongitude
= 참가자 출발 경도의 합 / 참가자 수
```

예를 들어 참가자가 3명이라면 다음과 같이 계산한다.

```text
centerLat = (lat1 + lat2 + lat3) / 3
centerLng = (lng1 + lng2 + lng3) / 3
```

계산된 중심 좌표는 이후 OpenAI 후보 생성과 Google Places 후보 검증의 기준점으로 사용한다.

---

## 3. 추천 지역 후보 생성

### OpenAI 사용 목적

중심 좌표 주변의 지역을 단순 거리순으로 선택하면 실제 모임 장소로 적합하지 않은 지역이 후보에 포함될 수 있다.

따라서 OpenAI를 이용하여 중심 좌표 주변에서 다음 조건을 고려한 지역 후보를 생성한다.

- 사람들이 실제로 약속 장소로 자주 사용하는 지역
- 상권이 형성되어 있는 지역
- 대중교통 접근성이 좋은 지역
- 음식점, 카페 등의 모임 장소를 찾기 쉬운 지역
- 중심 좌표에서 약 5km 이내에 위치한 지역

지역명은 지나치게 세분화된 행정동보다 사용자가 일반적으로 인식할 수 있는 지역명을 우선한다.

예:

```text
역삼동
논현동
신사동
```

최초 요청에서는 최대 10개의 후보 지역명을 생성한다.

OpenAI는 후보의 **지역명만 생성**하며 좌표는 생성하지 않는다. 실제 좌표와 지역 존재 여부는 Google Places API를 통해 검증한다.

---

## 4. 후보 부족 시 재시도

OpenAI가 생성한 후보라고 해서 모두 실제 추천 후보로 사용할 수 있는 것은 아니다.

Google Places 조회 실패, 대표 좌표 탐색 실패, 5km 범위 초과 등의 이유로 후보가 제외될 수 있다.

따라서 최초 후보를 Google을 통해 검증한 후 유효한 후보가 3개 미만이면 OpenAI에 한 번 더 후보 생성을 요청한다.

재요청 시 기존에 생성했던 지역은 제외하도록 전달한다.

```text
OpenAI 최초 후보 생성
        ↓
Google 검증
        ↓
유효 후보 3개 이상?
   ├─ YES → 다음 단계
   └─ NO
        ↓
기존 후보 제외 후 OpenAI 재요청
        ↓
Google 재검증
        ↓
유효 후보 3개 미만
        ↓
INSUFFICIENT_AREA_CANDIDATES 예외
```

## 5. 후보 지역 검증 및 대표 좌표 조회

OpenAI가 생성한 지역명은 Google Places API를 통해 실제 장소 정보로 변환한다.

추천 지역의 지도 표시 및 이동시간 계산을 위해 각 지역의 대표 좌표가 필요하다.

대표 위치는 다음 우선순위로 탐색한다.

```text
1순위: 해당 지역의 지하철역
2순위: 해당 지역의 버스 정류장
3순위: 해당 지역 자체의 대표 좌표
```

예를 들어 `역삼동` 후보라면 우선 지하철역을 검색하고, 적절한 결과가 없으면 버스 정류장 및 지역 자체를 순차적으로 조회한다.

Google Places Text Search의 location bias는 검색 결과의 위치를 강제로 제한하는 조건이 아니므로, Google 검색 결과를 그대로 신뢰하지 않는다.

조회된 좌표가 실제 중심 좌표 기준 5km 이내인지 별도로 검증한다.

---

## 6. 5km 거리 검증

후보 좌표와 중심 좌표 사이의 실제 거리를 계산하기 위해 Haversine 공식을 사용한다.

Google Places의 location bias와 별개로 서버에서 직접 거리를 계산한다.

```text
중심 좌표
    ↓
후보 대표 좌표
    ↓
Haversine 거리 계산
    ↓
5km 이내?
 ├─ YES → 유효 후보
 └─ NO  → 후보 제외
```

이를 통해 OpenAI 또는 Google 검색 결과가 추천 범위를 벗어나는 경우를 방지한다.

---

## 7. 참가자별 이동시간 계산

검증된 후보 지역에 대해 Google Routes Matrix API를 사용하여 참가자별 이동시간을 계산한다.

이동수단은 대중교통을 기준으로 한다.

```text
travelMode = TRANSIT
```

출발지는 참가자들의 출발 좌표이며 목적지는 각 추천 후보의 대표 좌표이다.

예를 들어 참가자 3명과 후보 지역 3개가 존재하면 다음과 같은 이동시간 데이터가 생성된다.

```text
참가자 A → 후보 1
참가자 A → 후보 2
참가자 A → 후보 3

참가자 B → 후보 1
참가자 B → 후보 2
참가자 B → 후보 3

참가자 C → 후보 1
참가자 C → 후보 2
참가자 C → 후보 3
```

모든 참가자가 이동 가능한 후보를 대상으로 추천 점수를 계산한다.

경로 계산 이후 이동 가능한 후보가 3개 미만이면 TOP3를 구성할 수 없으므로 `INSUFFICIENT_AREA_CANDIDATES` 예외를 발생시킨다.

---

## 8. 이동시간 지표 계산

각 후보 지역마다 다음 세 가지 값을 계산한다.

### 평균 이동시간

모든 참가자의 이동시간 평균이다.

```text
average =
    참가자 이동시간의 합 / 참가자 수
```

전체적인 이동 부담을 나타낸다.

### 최대 이동시간

해당 후보까지 가장 오래 걸리는 참가자의 이동시간이다.

```text
max = max(t1, t2, ..., tn)
```

특정 참가자에게 지나치게 불리한 지역을 방지하기 위해 사용한다.

### 이동시간 표준편차

참가자별 이동시간의 편차를 측정한다.

```text
stdDev =
    sqrt(
        Σ(time - average)^2 / 참가자 수
    )
```

표준편차가 작을수록 참가자들의 이동시간이 서로 비슷하다는 의미이다.

---

## 9. Min-Max 정규화

평균 이동시간, 최대 이동시간, 표준편차는 값의 범위가 서로 다르기 때문에 그대로 합산하지 않는다.

각 지표를 후보 집합 내에서 Min-Max 방식으로 정규화한다.

```text
normalized =
    (value - min) / (max - min)
```

정규화 결과는 기본적으로 `0 ~ 1` 범위를 가진다.

후보들의 값이 모두 동일하여 `max == min`인 경우에는 정규화 값을 `0`으로 처리한다.

---

## 10. 추천 점수 계산

정규화된 세 가지 지표에 가중치를 적용하여 최종 추천 점수를 계산한다.

```text
score =
      normalizedAverage * 0.4
    + normalizedMax * 0.4
    + normalizedStdDev * 0.2
```

가중치는 다음과 같다.

| 지표 | 가중치 | 의미 |
|---|---:|---|
| 평균 이동시간 | 40% | 전체 참가자의 전반적인 이동 부담 |
| 최대 이동시간 | 40% | 가장 불리한 참가자의 이동 부담 |
| 이동시간 표준편차 | 20% | 참가자 간 이동시간의 균형 |

모든 지표가 이동 부담을 나타내므로 **점수가 낮을수록 더 좋은 추천 지역**이다.

---

## 11. 추천 지역 TOP3 선정

모든 유효 후보의 추천 점수를 계산한 뒤 점수를 오름차순으로 정렬한다.

```text
score가 가장 낮은 후보
        ↓
TOP 1

두 번째로 낮은 후보
        ↓
TOP 2

세 번째로 낮은 후보
        ↓
TOP 3
```

최종적으로 상위 3개 지역만 추천 결과로 사용한다.

---

## 12. 추천 결과 저장

추천 실행 단위는 `RecommendationRun`으로 관리한다.

추천 결과가 정상적으로 생성되면 다음 데이터를 저장한다.

### RecommendationRun

```text
meetingId
status = COMPLETED
createdAt
updatedAt
```

### RecommendedArea

각 TOP3 지역에 대해 다음 데이터를 저장한다.

```text
recommendationRunId
areaName
createdAt
updatedAt
```

추천 계산 과정에서 사용한 다음 데이터는 DB에 영구 저장하지 않는다.

```text
중심 좌표
후보 지역 좌표
Google 이동시간
평균 이동시간
최대 이동시간
표준편차
정규화 값
추천 점수
```

Google에서 조회한 좌표와 이동시간은 추천 계산 또는 응답 생성 시에만 사용한다.

## 13. 추천 지역 조회 API

추천이 완료된 이후 다음 API를 통해 추천 지역을 조회한다.

```http
GET /api/meetings/{meetingId}/recommendations/areas
```

조회 흐름은 다음과 같다.

```text
meetingId
        ↓
가장 최근 COMPLETED RecommendationRun 조회
        ↓
RecommendationRun에 속한 RecommendedArea 조회
        ↓
저장된 지역명으로 Google Places 조회
        ↓
latitude / longitude 조회
        ↓
RecommendedAreaListResponse 반환
```

응답 예시는 다음과 같다.

```json
{
  "areas": [
    {
      "recommendedAreaId": 1,
      "name": "역삼동",
      "latitude": 37.5007,
      "longitude": 127.0385
    },
    {
      "recommendedAreaId": 2,
      "name": "강남동",
      "latitude": 37.8563,
      "longitude": 127.7018
    },
    {
      "recommendedAreaId": 3,
      "name": "서초동",
      "latitude": 37.4884,
      "longitude": 127.0168
    }
  ]
}
```

위도와 경도는 DB에 저장된 값이 아니라 조회 시 Google Places API를 통해 얻은 값이다.
