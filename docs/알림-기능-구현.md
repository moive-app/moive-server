# 알림 기능 구현 원리

## 1. 알림이 어떻게 동작하는가?

이벤트 하나가 발생하면 두 가지가 동시에 일어난다.

```
이벤트 발생 (모임 생성, 조건 입력 완료 등)
        ↓
  ① DB에 알림 저장   →  알림함(GET /api/notifications)에서 조회 가능
  ② FCM 푸시 발송   →  기기 상단에 OS 푸시 알림 표시
```

둘은 독립적이다. OS 알림 권한을 거부해도 ①은 항상 저장된다.

---

## 2. FCM이란?

**Firebase Cloud Messaging** — 구글이 제공하는 무료 푸시 알림 서버다.

```
우리 서버  →  FCM 서버  →  사용자 기기
```

우리 서버가 직접 기기에 푸시를 보내는 게 아니라, FCM 서버에 "이 토큰의 기기에 보내줘" 라고 요청하면 FCM이 대신 전달해준다.

**왜 FCM을 쓰는가?**
- 직접 기기에 보내려면 Android/iOS별 프로토콜을 각각 구현해야 함
- FCM이 이걸 대신 처리해줌
- 완전 무료

---

## 3. FCM 토큰이란?

앱을 설치한 **각 기기를 식별하는 고유 문자열**이다.

```
사용자 A
├── 기기 1 (핸드폰)   → fcm_token: "abc123..."
└── 기기 2 (태블릿)   → fcm_token: "xyz789..."
```

- 앱 실행 시 FE가 FCM SDK로 토큰을 발급받음
- 발급된 토큰을 `PUT /api/devices/token`으로 백엔드에 등록
- 로그아웃 시 `DELETE /api/devices/token`으로 제거

한 사용자가 여러 기기를 쓰면 **모든 기기로 동시에 푸시**가 간다.

---

## 4. 알림 발송 흐름 (코드 기준)

```
NotificationService.sendNotification(userId, meetingId, type, content)
        ↓
  1. Notification 엔티티 생성 → DB 저장 (알림함)
  2. device_tokens 테이블에서 해당 userId의 FCM 토큰 목록 조회
  3. 토큰이 있으면 FcmService.sendToTokens() 호출
  4. FCM 서버로 HTTP 요청 → 기기에 푸시
```

토큰 하나씩 전송하며, 실패해도 다음 토큰은 계속 시도한다. 한 기기 실패가 전체에 영향을 주지 않는다.

---

## 5. 알림 발송 시점 (연결 위치)

| 알림 | 발송 시점 | 연결된 위치 |
|------|----------|------------|
| NOTI-001 조건 입력 요청 | 모임 생성 / 참여 시 | `MeetingService.createMeeting()`, `joinMeeting()` |
| NOTI-003 장소 투표 요청 | 전원 조건 입력 완료 → VOTING 전환 시 | `MeetingService.submitPreference()` |
| NOTI-002 장소 추천 완료 | 추천 알고리즘 완료 시 | 추후 연결 (재경님 파트) |
| NOTI-004 모임 확정 | 장소 투표 확정 시 | 추후 연결 (장소 투표 기능 구현 후) |

## 6. 자동 읽음 처리

특정 행동을 직접 완료하면 관련 알림이 자동으로 읽음 처리된다.

| 행동 | 자동 읽음 처리 알림 |
|------|-------------------|
| 조건 입력 완료 | 해당 모임의 NOTI-001 |
| 장소 투표 완료 | 해당 모임의 NOTI-003 (투표 기능 구현 후 연결 예정) |

```java
// MeetingService.submitPreference() — 첫 제출 시
notificationService.autoReadByType(userId, meetingId, NotificationType.COND_INPUT);
```

## 7. 커서 기반 페이지네이션

알림 목록은 무한스크롤 방식이다. 페이지 번호(offset) 방식이 아닌 커서(cursor) 방식을 쓴다.

**offset 방식의 문제점**
```
1페이지 조회 → 새 알림 추가됨 → 2페이지 조회 시 중복 발생
```

**cursor 방식**
```
첫 요청: cursor=null, size=20
  → ID 100~81번 알림 반환, nextCursor=81

다음 요청: cursor=81, size=20
  → ID 80번부터 조회 → 중복 없음
```

항상 `size+1`개를 조회해서 `hasNext` 여부를 판단하고, 실제 응답엔 `size`개만 담는다.

## 8. 안읽음 뱃지 (홈 화면 red-dot)

```
GET /api/notifications/unread-status
→ { "hasUnread": true }
```

30일 이내 안읽은 알림이 1개 이상이면 `true`. 홈 화면 알림 아이콘에 빨간 점 표시 여부를 판단하는 용도다.
